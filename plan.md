# AstroQuiz — Plan

A Salesforce quiz game on an Experience Cloud **LWR** site, built in LWC and Apex only. Players join as
**guests** (nothing about their game is kept) or **register** with a nickname and email to get a
personal key, which lets them log in later and appear on the leaderboard. Questions come from a bank that
the AI keeps stocked.

This plan replaces the earlier spec. It is written against what exists in the org today (section 2) and
describes where the project should end up (sections 3–9).

---

## 1. Decisions and constraints

| # | Decision | Why |
|---|---|---|
| D1 | **No Salesforce `User` records for players.** A registered player is a `Contact`. | No Experience Cloud licences, no guest-versus-member profile juggling, no `@salesforce/user` or `Network` imports (they broke LWR in Locker). |
| D2 | **Our own Register and Login screens**, built as LWC, not the platform Login/Register pages. | Full control of the flow; the whole site can stay public. |
| D3 | **Login = email + personal key.** The key is generated by the server after registration, shown once, and only its hash is stored on the Contact. | No passwords to manage or leak. |
| D4 | **Guests leave no records.** Their game rooms are deleted shortly after the game ends, and they get no leaderboard entry. | Stated requirement. |
| D5 | **The guest user is never stamped on a record** (owner, player or leaderboard fields). | Stated requirement. Rooms are owned by a real admin. |
| D6 | **Games mix every topic.** There is no topic filter. | Stated requirement. |
| D7 | **The AI generates questions automatically** (on demand during a game, and on a schedule). Generated questions are saved as Approved. | Stated requirement: guests must not depend on an admin. |
| D8 | **At most 5 Apex classes and 5 LWCs.** Services, selectors, DTOs and jobs are inner classes. | Stated requirement. |
| D9 | **Every class is `without sharing`, API 60, and granted in the permission sets.** | Stated requirement. |
| D10 | **No test classes.** | Stated requirement. (A production deploy needs 75% coverage, so this only works for sandboxes and dev orgs.) |

## 2. Current state (as of 2026-10-09)

**Org:** `salesforce-quizorg` (Developer Edition). **Site:** `Salesforce_Dev_Arena1` (LWR, "Build Your Own"
theme). The Home route is public. A custom `Question_Admin__c` route (`/question-admin`) exists.

### What works
- Game flow: create room, join, lobby, start, timed questions, scoring, reveal, results. Verified by calling the
  services directly as admin; the full flow in a browser has not been confirmed since the last fixes.
- Question generation with the **Einstein Models API** (`sfdc_ai__DefaultGPT4Omni`). Tested as admin: 3
  questions in about 5 seconds. It does not need the Prompt Template User permission set.
- Question Admin page (review, edit, approve, retire, add material, generate).
- Leaderboard (signed-in users only), game purge 5 minutes after a game finishes.

### Data in the org
- Question bank: 5 sample questions (Beginner, Apex, one per type) plus 6 AI-generated (3 Advanced SOQL, 3
  Intermediate Data Modeling), all Approved. One generated question is invalid ("SELECT * in SOQL"), so the
  auto-approval needs a quality check (section 7).
- No game rooms, players, answers or leaderboard entries exist yet.
- The `QuizCleanupBatch` schedule (cleanup and bank top-up) is **not scheduled**.

### Rules the data enforces (found the hard way)
- `Game_Room__c`: Question Count 5–20, Max Players 1–20, Solo requires Max Players = 1, Seconds Per Question 5–120.
- Restricted picklists: question types are `MCQ_SINGLE`, `MCQ_MULTI`, `TRUE_FALSE`, `CODE_OUTPUT`, `SCENARIO`;
  topics include `Data Modeling` (with a space); `AI_Generation_Log__c.Status__c` is `Queued/Running/Success/Partial/Failed`.
- `Question__c.Question_Hash__c` is unique (used for de-duplication).

### Lessons already paid for
1. **LWR + Locker:** `@import 'c/otherComponent'` in CSS resolves to that component's JavaScript class and crashes
   with "Class constructor … cannot be invoked without 'new'". Never `@import` a component. Avoid platform-scoped
   imports (`@salesforce/user/*`, `@salesforce/community/*`, `lightning/navigation`) in game components.
2. **"Script-thrown exception":** re-wrapping an `AuraHandledException` replaces its message. Controllers must
   `catch (AuraHandledException e) { throw e; }` before the generic catch.
3. **Anonymous Apex** cannot throw `AuraHandledException` and cannot use `SYSTEM_MODE`, which affects how we test.
4. **Callouts must come before DML** in a transaction. The generation code does all model calls first.
5. Admin users have no field-level access to most game fields. Anonymous debugging queries fail on them; use the
   admin controller methods instead.

## 4. Player identity without `User` records

### 4.1 Contact fields (new, on `Contact`)

| Field | Type | Purpose |
|---|---|---|
| `Quiz_Nickname__c` | Text(20), unique | Public display name |
| `Quiz_Key_Hash__c` | Text(64) | SHA-256 of key + salt (never the key itself) |
| `Quiz_Key_Salt__c` | Text(32) | Per-contact salt |
| `Quiz_Session_Hash__c` | Text(64) | Hash of the current session token |
| `Quiz_Session_Expires__c` | DateTime | Session expiry (default 30 days) |
| `Quiz_Failed_Logins__c` | Number | Consecutive failed attempts |
| `Quiz_Locked_Until__c` | DateTime | Lockout end |
| `Quiz_Is_Player__c` | Checkbox | Marks quiz contacts (keeps them apart from any other Contacts) |

Contacts are created **without an Account** (private contacts) and owned by the record-owner admin (D5).
`Email` is the login id; uniqueness is checked in Apex (case-insensitive), and the standard duplicate rule is
handled explicitly.

### 4.2 Register

1. Player opens **Register** in `quizAccount` and enters **nickname** and **email**.
2. `QuizGameController.register(nickname, email)` validates length, characters and email format,
   rejects duplicate email or nickname, and rate-limits by IP-less token (see 8).
3. `QuizAccountService` creates the Contact, generates the **key**, stores `hash(key + salt)`, creates a session,
   and returns `{ key, sessionToken, nickname }`.
4. The screen shows the key **once** with a Copy and Download button and the warning "we cannot show it again".
5. The session token goes into `localStorage`; the player is now signed in.

**Key format:** `AQ-XXXX-XXXX-XXXX`, 12 characters from the unambiguous alphabet already used for room codes
(`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`), generated with `Crypto.getRandomInteger()` (about 60 bits).

### 4.3 Login

1. Player enters **email** and **key** in `quizAccount`.
2. `QuizGameController.login(email, key)` finds the Contact, checks `Quiz_Locked_Until__c`, compares hashes,
   and on success resets the failed counter and issues a new session token. On failure it increments the
   counter and locks the account for 15 minutes after 5 misses. The error message never says which part was wrong.
3. Every later call sends the session token; the server hashes it and finds the Contact, so there is no `User`.

### 4.4 Recovery (phase 2)
A lost key cannot be recovered, only **reissued**: email a one-time link to the Contact's address, then generate
a new key and invalidate the old hash. Until this exists, show a clear warning at registration.

### 4.5 What changes in the data model

| Object | Change |
|---|---|
| `Player__c` | Replace `User__c` with `Contact__c` (lookup). Guests leave it empty. |
| `Leaderboard_Entry__c` | Replace `User__c` with `Contact__c`. Nickname is copied from the Contact. |
| `User_Question_History__c` | Replace `User__c` with `Contact__c`, or drop the object (see section 9). |
| `Game_Room__c` | `Topic__c` stays on the object but is left empty. |
| Permission sets | Remove all `User`-related access, add field access for the new Contact fields. |

Guest versus member is simply "does the call carry a valid session token". The site no longer needs to know who
the Salesforce user is, so `isGuest` and the Login/Register routes drop out of the game components entirely.

## 5. Game flow

1. **Create:** `createRoom(level, types, count, maxPlayers, nickname)` → pick questions (5.1), insert the room
   (owner = record-owner admin), insert the host player, return the room code and a player token.
2. **Join:** `joinRoom(code, nickname)` while the room is in Lobby.
3. **Start:** host only; sets `Started_At__c = now + 3 s`.
4. **Play:** clients poll `getRoomState` every 2.5 s. The server derives the question number and phase
   (answering or reveal) from the clock; `submitAnswer` rejects late or duplicate answers.
5. **Finish:** room becomes Finished, a leaderboard entry is written for each player with a session
   contact, and a job deletes the whole room 5 minutes later so every client can read the final standings.

### 5.1 Picking questions
- Level only, all topics, selected question types. Prefer questions the player has not seen.
- If short: relax the types, then allow seen questions, then **generate on demand** (section 7).
- The count is clamped to 5–20 and players to 1–20 on the server, whatever the client sends.
- If fewer than 5 questions exist after all of that, show the real reason (never "Script-thrown exception").

### 5.2 Scoring
Base points by level + speed bonus + streak bonus, all from `Quiz_Config__mdt` (Beginner 10, Intermediate 20,
Advanced 30; speed bonus up to 10; streak bonus 2 per step, capped at 10).

## 6. Guests, members and what is stored

| | Guest | Registered player |
|---|---|---|
| Needs an account | No | Contact with nickname + email + key |
| Room, players, answers | Created for the game, deleted 5 minutes after it ends | Same |
| Leaderboard entry | None | One per finished game, kept |
| Question history | None | Kept, so repeats are avoided |
| Owner on room | Record-owner admin | Record-owner admin |
| Guest user on any field | Never | Never |

`CreatedBy` and `LastModifiedBy` cannot be changed and may show the site guest user on rooms for the few minutes
they exist. Contacts created by registration are the only records that stay.

## 7. Question supply

- **On demand:** when a game is short, up to 4 model calls (3 questions each) rotate through all topics and the
  selected types, then save as Approved. Roughly 10 seconds the first time; later games are instant.
- **Top-up:** the hourly job finds the level with the fewest approved questions (under
  `Min_Bank_Size_Per_Bucket__c` = 20) and generates for it.
- **Admin path:** Question Admin can still paste study text, chunk it, and generate Drafts for review.
- **Quality gate to add:** auto-approval is risky (one invalid question already slipped through). Add a second
  model call that checks each question (correct answer present, one valid option, no invalid syntax) and keeps
  failures as Draft.
- **Unconfirmed:** whether the Models API can be called by the **guest user**. Admin works. If a guest call is
  refused, it is logged and the game falls back to what the bank has, and the hourly top-up becomes the
  dependable path.

## 8. Security

- No raw keys or session tokens are stored anywhere, only hashes.
- Constant-time comparison for key and token checks.
- Rate limits (counters in `Quiz_Config__mdt`-driven logic, stored on the Contact or a short-lived cache): registration,
  failed logins, room creation and answers per minute.
- Every query is scoped to the room code plus a verified token; the correct answer is never sent to the client
  until the reveal phase.
- Inputs are validated server-side: nickname length and characters, email format, picklist values, counts.
- Question Admin requires the `Quiz_Admin_Access` custom permission, enforced in Apex.
- Guest class access is limited to the controllers; no direct object access for the guest profile.

## 9. Open decisions

1. **`User_Question_History__c`:** keep it (re-pointed to Contact) or drop it? Dropping removes an object; the cost
   is that registered players may see repeats.
2. **Key recovery:** is "reissue by email link" needed for launch, or is a clear "save your key" warning enough?
3. **Do you want an optional password** later, or stay key-only?
4. **Contact visibility:** keep quiz Contacts private (no Account), or place them under a single "AstroQuiz Players"
   Account so reports are easier?

## 11. Success checks

- A guest plays Solo and Multiplayer to the end; nothing about the game remains after 5 minutes.
- A new player registers, sees their key once, logs out, logs back in with email + key, and finishes a game that
  appears on the leaderboard under their nickname.
- Three wrong key attempts do not reveal whether the email exists; five lock the account for 15 minutes.
- An Advanced game with an empty Advanced bank generates questions and starts, or shows a clear reason.
- No `Player__c`, `Room_*` or `Leaderboard_Entry__c` record references the site guest user.
- The project contains exactly 5 Apex classes and 5 LWCs.
